# 명상 가이드 서비스 설계 명세 (구현 기준)

**문서 성격**: 현재 코드베이스에 실제 구현된 명상 가이드( Guidance ) 서비스를 설계·명세 형태로 정리한 문서.  
**대상**: MoodTalk v2.0 Guidance Pipeline (Chunk 방식 자막 생성 + TTS 스타일 + 피드백).

---

## 1. 개요

### 1.1 역할

- **POST /api/guidance/generate**: STRICT6 인테이크 + 선택 테마 + (선택) face_data·session_id·cursor 를 받아, **자막(captions)** 과 **TTS용 메타(voice_profile, tts_instruction, tts_speed)** 를 반환. TTS 재생·음성 합성은 클라이언트 책임.
- **POST /api/guidance/feedback**: 명상 종료 후 **만족도 피드백**(best_moments, worst_moments, user_rating 등) 저장.

### 1.2 출력 단위 (MVP)

- 요청 1회당 **GuidanceAction 1개** 기준. **captions** 는 **최대 2개**(2줄)만 반환.
- Chunk 연속: `cursor=null` 로 시작 → 응답의 `next_cursor` 로 다음 Chunk 요청 → 2~3회 호출로 시나리오 진행.

## 2. API 계약

### 2.1 POST /api/guidance/generate

**Request: GuidanceGenerateRequest**

| 필드 | 타입 | 필수 | 설명 |
|------|------|------|------|
| intake | StrictIntakeInput | O | STRICT6 인테이크 (core_emotion, intensity, face_data 등) |
| selected_theme_id | string | O | 선택된 테마 ID |
| signal_degrade | bool | - | 기본 false. true 면 standard_grounding Failover |
| confidence | float | - | null 이면 failover는 signal_degrade 만 사용 |
| cursor | GuidanceCursor | - | 다음 Chunk 시 이전 응답의 next_cursor 전달 |
| session_id | string | - | 명상 런 ID. Chunk마다 동일 값 전달 시 TTS 스타일 상태(쿨다운/히스테리시스) 유지 |

**Response: GuidanceOutputState**

| 필드 | 타입 | 설명 |
|------|------|------|
| guidance_id | string | UUID (요청마다 신규) |
| captions | CaptionItem[] | 자막 목록 (최대 2개) |
| silence_ms | int | 자막 간 침묵(ms). arousal 기반 계산 |
| voice_profile | string | 기본 "qwen_female_calm". TTS 프로필명 |
| tts_instruction | string? | CosyVoice 톤 지시 (face_data 기반 Hybrid Pacing). 있으면 클라이언트가 TTS에 적용 |
| tts_speed | float? | TTS 재생 속도 배율 (0.5~2.0). 있으면 클라이언트가 TTS에 적용 |
| action_context | object? | GuidanceAction 직렬화 |
| next_cursor | GuidanceCursor? | 다음 Chunk 요청 시 사용. 없으면 시나리오 종료 |
| decision_trace | string[] | 추천/생성 결정 근거 로그 |
| meta | object | is_failover, model 등 |

**CaptionItem**

| 필드 | 타입 | 설명 |
|------|------|------|
| seq | int | 순서 (1부터) |
| text | string | 표시 텍스트 |
| hold_ms | int | 표시 유지 시간(ms) |
| type | string? | intro, advice, main, outro 등 |

**GuidanceCursor**

| 필드 | 타입 | 설명 |
|------|------|------|
| scenario_id | string | 시나리오 ID |
| next_block_index | int | 다음에 생성할 블록 인덱스 |

## 3. 백엔드 처리 흐름 (generate)

```
GuidanceGenerateRequest
  │
  ├─ decide_action(intake, selected_theme_id; signal_degrade, confidence)
  │     → PolicyEngine: 테마별 GuidanceAction, scenario_blocks 로드, guide_tone, task_atom 결정
  │     → Failover: signal_degrade=True 또는 confidence < 0.4 → scenario_id=standard_grounding
  │
  ├─ render_scenario_chunk(action, intake, cursor, use_qwen=True)  또는  render_captions(...)
  │     → NLG: intake.face_data → face_desc (표정·호흡·심박 문구)
  │     → resolve_arousal_level(intake) → hold_ms / silence_ms 보정
  │     → Qwen(vLLM) 각색 또는 로컬 템플릿 → CaptionItem[] (최대 2개), next_cursor
  │
  ├─ resolve_arousal_level(intake), compute_silence_ms(arousal) → silence_ms
  │
  ├─ [TTS 스타일] session_id 와 intake.face_data 가 있으면:
  │     face_data_from_intake_dict(face_data) → FaceData
  │     get_voice_style_manager(session_id) → VoiceStyleManager
  │     manager.determine_style(face_data) → TTSConfig → tts_instruction, tts_speed
  │
  └─ GuidanceOutputState(guidance_id, captions, silence_ms, voice_profile,
                         tts_instruction?, tts_speed?, action_context, next_cursor,
                         decision_trace, meta)
```

## 4. 정책 엔진 (PolicyEngine)

- **파일**: `backend/core/policy_engine.py`
- **역할**: StrictIntakeInput + selected_theme_id → GuidanceAction + decision_trace. LLM은 액션 결정에 사용하지 않음.

### 4.1 테마 라이브러리 (THEME_LIBRARY)

| theme_id | title | estimated_min | summary |
|----------|--------|----------------|---------|
| self_compassion | Self-Compassion (자기 자비) | 8 | 타인의 시선에서 벗어나 스스로를 진정, 안전감 회복 |
| thought_labeling | Thought Labeling (인지적 거리두기) | 6 | 자동사고를 '생각'으로 분리, 과잉 동일시 완화 |
| micro_task_bridging | Micro-Task Bridging (실행 트리거) | 5 | 명상 종료 직후 1개 행동으로 업무 재진입 |

### 4.2 Failover

- `signal_degrade=True` 또는 `confidence < 0.4` → **scenario_id=standard_grounding**, 레퍼런스 시나리오만 사용.

### 4.3 테마별 액션 (Rule 기반)

- 테마별 phase / block_type / scenario_id 고정. scenario_blocks 는 `data/scenarios.json` 에서 scenario_id 로 로드.
- **guide_tone**: 사용자 선택(guide_tone) 우선, 없으면 테마별 기본값 (self_compassion→warm, thought_labeling→rational, micro_task_bridging→strict).
- **activation** 단계: TaskAtomChooser(Lite/Pro)로 task_atom 결정. 시나리오 default_task 존재 시 활용.

### 4.4 사용자 맞춤 추천 3가지 (제안)

#### 방향성

| 현재 | 보완 |
|------|------|
| 테마 3종을 그대로 보여 주고 사용자가 하나 고름. | 사용자 의도/상황을 한 번 끌어낸 뒤, 그에 맞춰 **“맞는 명상 3개”**를 추려서 추천. |
| | (A)(B)(C)는 그대로 두고, **“무엇을 추천할지”만** 사용자 맞춤으로 바꾸는 구조. |

#### 2. 유추(끌어내기) 방법 제안

| 옵션 | 내용 | 비고 |
|------|------|------|
| **A** | **짧은 선택지** — 명상 진입 전 “지금 어떤 걸 원하세요?” 한 화면. 예: 편안해지기 / 집중·멈춤 / 자기 자비 / 잠들기 / 스트레스 풀기 / 그냥 흐름대로 등 5~6개. 선택 1~2개 → 백엔드에서 테마/시나리오와 매핑해 상위 3개 추천. | 가장 단순 |
| **B** | **STRICT6만으로 유추** — 지금처럼 감정 입력(STRICT6)만 받고, core_emotion, situation_context, intensity(및 immediate_goal)로 “이 사용자에게 맞는 명상 방향” 점수 계산. PolicyEngine에 추천 점수만 추가: 테마 3종에 점수 부여 → 상위 3개를 “추천 3개”로 노출. **추가 질문 없이** 지금 플로우만으로 “맞는 3개” 가능. | 이미 있는 데이터 활용 |
| **C** | **선택지 + STRICT6** — “지금 원하는 방향” 짧은 선택지 1번 + STRICT6. 선택지로 “의도”, STRICT6로 “감정 강도·맥락” 보정 → 둘을 합쳐 추천 3개 계산. | 유추 정확도 높임 |

#### 3. “가장 잘 맞는 3개 추천” 노출 방식

| 현재 | 보완 |
|------|------|
| 테마 선택 화면에서 3종 전부 동일하게 노출. | 같은 3종 테마를 유지하되 **순서를 “추천 순”으로** 바꾸고, 상위 1~3에 “추천” 뱃지 또는 “당신에게 맞는 순서” 문구. |
| | 또는 “오늘의 추천 3가지” 블록을 두고 그 안에 위 3개를 넣고, “다른 테마도 보기”로 전체 목록 펼치기. |

- 추천 3개 = 기존 테마 3종을 **“맞춤 순서”로 재정렬**해도 되고, 나중에 시나리오가 늘어나면 **“전체 N개 중 상위 3개”**로 확장하면 됨.

#### 4. (A)(B)(C)와의 관계

| 구성요소 | 변경 여부 |
|----------|------------|
| **(A) 스크립트** | 그대로. “추천”은 어떤 시나리오/테마를 골라서 보여줄지만 바꿀 뿐, 스크립트 소스(자사 + LLM 각색)는 동일. |
| **(B) TTS** | 변경 없음. |
| **(C) 배경음** | 변경 없음. |
| **실시간 LLM** | 그대로 “없어도 됨”. 유추는 선택지/STRICT6 규칙(또는 경량 점수)으로만 해도 되고, 실시간 LLM은 쓰지 않아도 됨. |

#### 5. 구현 난이도·우선순위 제안

| 단계 | 내용 | 난이도 |
|------|------|--------|
| **1** | STRICT6만으로 테마 3종에 점수 매겨서 “추천 순서”로 정렬해 노출. **(옵션 B)** | 낮음 |
| **2** | 명상 진입 전 “지금 원하는 방향” 선택지 1페이지 추가 후, 선택지+STRICT6로 추천 3개. **(옵션 C)** | 중간 |
| **3** | 시나리오/테마가 3개보다 많아지면 “전체 중 상위 3개” 추천으로 확장. | 이후 |

먼저 **옵션 B(STRICT6만으로 추천 3개)**로 가져가면, “(A)(B)(C) 기반 + 사용자에게 맞는 방향 유추해서 3개 추천”이라는 제안 방향을 가장 빠르게 반영할 수 있다.

## 5. NLG 서비스

- **파일**: `backend/services/nlg_service.py`
- **역할**: GuidanceAction + intake → CaptionItem[] (Chunk당 최대 2줄), next_cursor. Qwen(vLLM) 각색 또는 로컬 템플릿 폴백.

### 5.1 face_data → face_desc (NLG용)

- `intake.face_data` (dict): dominant_emotion, intensity, breath_rate, heart_rate, heart_rate_confidence 등.
- face_desc 문자열: 표정/강도, 호흡(느림/정상/빠름), 심박(heart_rate_confidence ≥ 0.4 일 때만 "약 N BPM" 포함). NLG 시스템 메시지에 "표정/강도: {face_desc}" 로 전달.

### 5.2 각성 → 타이밍

- **resolve_arousal_level(intake)**: arousal_level 우선, 없으면 intensity/10, 없으면 face_data.intensity/arousal. 기본 0.5.
- **compute_hold_ms(blk, pace, arousal_level)**: pace 기본값 + arousal 보정 (고각성 → hold 길게).
- **compute_silence_ms(arousal_level)**: 고각성 1500ms 근처, 저각성 700ms 근처 (SILENCE_MS_MIN~MAX 내).

### 5.3 Chunk 규칙

- cursor 가 가리키는 블록부터 **최대 2블록**만 처리.
- Qwen 출력: "\n" 으로 split, **2줄 초과 시 None → 로컬 base_text 폴백**. DENYLIST_PHRASES·task_atom 포함 검사 후 CaptionItem 생성.
- **next_cursor**: 다음 블록 인덱스가 blocks 길이 미만이면 반환, 아니면 null.

## 6. TTS 스타일 (Hybrid Pacing Engine)

- **파일**: `backend/services/voice_style_manager.py`, `backend/types/voice_schema.py`
- **역할**: session_id + intake.face_data 가 있을 때만, 실시간 생체 데이터로 TTS 톤·속도 결정. **CosyVoice(Qwen3-TTS) 호출은 클라이언트 책임.**

### 6.1 입력 (FaceData, intake.face_data dict 변환)

| 필드 | 타입 | 설명 |
|------|------|------|
| tension_delta | float | 긴장도 변화량 (baseline 대비) |
| heart_rate | int | 심박수 BPM |
| heart_rate_confidence | float | 0.0~1.0 |
| perclos | float | 졸음 척도 0~1 |
| quality | float | 얼굴 검출 품질 0~1 |
| timestamp | float | 초 단위 (예: time.time()) |

- **face_data_from_intake_dict(d, timestamp?)**: dict → FaceData. 키 없으면 기본값 사용. 변환 실패 시 None → TTS 스타일 미적용.

### 6.2 출력 (TTSConfig → 응답 필드)

- **tts_instruction**: CosyVoice 톤 지시 문자열 (예: "calm and soothing tone", "clear and energetic tone", "neutral tone").
- **tts_speed**: 재생 속도 배율 (Calm 0.8, Neutral 1.0, Awake 1.1 등).

### 6.3 상태 규칙 (R1~R4)

- **R1 Cooldown**: 스타일/속도 변경 후 **15초** 동안 변경 금지.
- **R2 Hysteresis**: Calm 진입 `tension_delta > 0.20` 이 **3초 이상** 지속 시. Calm 이탈 `tension_delta < 0.12` 이 **8초 이상** 지속 시 Neutral 복귀.
- **R3 Quality Gating**: `quality < 0.5` 또는 `heart_rate_confidence < 0.4` → 무조건 Neutral, speed 는 0.95~1.05 구간 스무딩.
- **R4 Emotional Acting Limit (MVP)**: 톤·속도만 사용. Calm(instruction=calm and soothing, speed=0.8), Awake(perclos>0.6 → clear and energetic, 1.1), Neutral(1.0).

### 6.4 세션별 상태

- **get_voice_style_manager(session_id)**: 세션별 VoiceStyleManager 캐시 (최대 500 세션). 동일 session_id 로 Chunk 요청 시 쿨다운·히스테리시스가 유지됨.

## 11. 요약

- **Generate**: PolicyEngine(테마·Failover) → NLG(Chunk 2줄, face_desc·arousal·hold/silence) → (선택) VoiceStyleManager(tts_instruction, tts_speed) → GuidanceOutputState.
- **Feedback**: GuidanceFeedbackRequest → guidance_feedback_service → JSONL append.
- **TTS**: 서버는 instruction/speed 메타만 반환; 실제 음성 합성·재생은 클라이언트에서 수행.

## 12. 사용자 만족도·안정성·성능 향상 방향

갭 분석 및 PM 제안을 반영한 **설계 명세 수준**의 향상 방향. 구현 우선순위는 §10(갭 분석 문서) 및 백로그와 연동해 조정한다.

### 12.1 만족도

| 방향 | 내용 |
|------|------|
| 피드백 활용 | best_moments / worst_moments · user_rating 이미 수집. 추후 가중치·추천 반영. |
| 세션 적응 | 세션 길이·개입 선택(호흡/바디스캔/EFT/재진입)을 상태 기반으로 조절 → “딱 맞는 양” 제공, 완주율·재방문 향상. |
| TTS 품질 | TTS 스키마 확장·CosyVoice 2/3급 제어로 체감 품질 향상. |

### 12.2 안정성

| 방향 | 내용 |
|------|------|
| crisis_gate | **파이프라인 최전방**에 고정. ingest(face_data + 인테이크) → **crisis_gate** → (ok일 때만) state_estimator → policy → nlg → tts. 위기 시 LLM 우회, 고정 안내만 반환. |
| **quality 게이팅 불일치(즉시 개선)** | 검증 결과 유일한 명시적 불일치: **quality < 0.5 → face_data 생략 또는 기본값** 명세는 있으나 미구현. 프론트에서 null 전송 또는 백엔드에서 quality로 가중/생략 처리 추가 시 안정성 격차 해소. |
| 게이팅 유지 | quality/confidence 게이팅, 쿨다운/히스테리시스 유지(채터링·과반응 방지). |
| trace 표준화 | decision_trace에 **crisis_trigger**, **action_taken**, **locale_resources** 등 안전 필드 표준화 → 감사·규제 대응. |

### 12.3 성능(체감)

| 방향 | 내용 |
|------|------|
| 타이밍 적응 | hold_ms/silence_ms · arousal 적응 유지. |
| 상태 추정 | HRV 도입 시 스트레스/이완 추정 정확도 향상 → 맞춤도·효과성 향상. |
| 세션 길이 적응 | (Phase 2) 안정화가 빠르면 종료·불안정이면 호흡 연장 등으로 “너무 길다/짧다” 불만 감소. |

## 13. 연산 속도 확보 전략

처리 속도·서버 부하를 줄여 **crisis_gate·HRV·TTS 확장**을 지연 없이 반영하기 위한 전략. 설계 명세에 포함해 구현 시 참조한다.

### 13.1 1단계: Groq Cloud API (LLM 속도)

| 항목 | 내용 |
|------|------|
| 목적 | NLG(Qwen/vLLM) 병목 해소. **저지연·스트리밍** 지원으로 crisis_gate 등 안전 로직을 앞에 넣어도 체감 지연 완화. 목표 SLO(응답 시간 등)는 서비스에서 별도 정의. |
| 적용 | `nlg_service`의 vLLM 호출부를 **Groq API** 호출로 대체(또는 폴백 옵션). OpenAI 호환 스타일, 무료 티어 제공. |
| 주의 | Groq 모델(Llama 3, Qwen 등)의 **한국어·프롬프트 품질** 검증. 장기 벤더/가격 정책 리스크 검토. |

### 13.2 2단계: OpenAI Realtime API (음성·지연)

| 항목 | 내용 |
|------|------|
| 목적 | STT+LLM+TTS 통합, **저지연·실시간 인터랙션** 지원. 음성 파이프라인 중간에 crisis_gate 삽입 가능. 목표 SLO는 네트워크·모델·리전에 따라 정의. |
| 적용 시점 | 현재는 **자막/캡션 중심**이면 1단계(Groq)만으로 충분. **음성 우선·실시간 대화** 기능 도입 시 2단계로 검토. |
| 주의 | WebSocket·음성 스트리밍으로 현재 REST generate → captions → TTS와 **아키텍처 상이**. Realtime 과금 검토. |

### 13.3 3단계: 프론트 rPPG/HRV 연산 분산

| 항목 | 내용 |
|------|------|
| 목적 | rPPG·얼굴 분석은 이미 프론트. **HRV(SDNN 등)**까지 **WASM 또는 TensorFlow.js**로 클라이언트 연산, 서버에는 가공된 수치만 전송 → 서버 부하·처리 속도 문제 완화. |
| 적용 | 프론트 rPPG 파이프라인 확장, face_data에 HRV 필드 추가. 백엔드는 crisis_gate·policy·NLG에 집중, HRV는 스키마만 수용. |
| 주의 | 저사양 기기에서는 배터리·발열 고려. HRV는 **선택 기능** 또는 품질/프레임 조절 옵션 권장. |

### 13.4 보안·키 관리 및 트레이드오프

| 항목 | 내용 |
|------|------|
| API 키·세션 | **클라이언트(브라우저)에 API 키 직접 노출 금지**. Groq/OpenAI 등 외부 API는 백엔드 프록시 경유. Realtime·WebRTC 도입 시 세션 토큰·키 노출 리스크 검토 필수. |
| 트레이드오프 | 연산 속도 전략은 **속도만이 아니라 보안·비용·벤더 의존**과 함께 설계. 속도 vs 보안(키 경유), vs 비용(과금), vs 벤더락(장기 가격·정책)을 서비스 정책에 맞게 균형. |

## 14. 블록 플래너(LLM) 명세 — 전부 정리

기존 Guidance API에 **블록 플래너(LLM)** 단계를 최소로 추가. 성공 시 LLM blocks 순서로 시나리오 실행, 실패 시 기존 scenarios.json 고정 시나리오로 폴백. GPU 없이 기존 NLG(vLLM or API) 호출로 붙인다.

---

### 14.1 목표 (MVP-0)

| 항목 | 내용 |
|------|------|
| 목표 | **세션 시작 시 1회** LLM에게 "블록 조합 JSON만" 받기 → 서버 검증 통과 시 그 블록 순서로 시나리오 실행. 실패 시 **기존 scenarios.json 고정 시나리오**로 폴백. 기능 회귀 없음. |
| 호출 | 기존 NLG와 동일 경로(vLLM or API). GPU 없어도 됨. |

---

### 14.2 Cursor에게 시킬 작업 4개 (P0)

1. **Block DSL 스키마 추가** (Pydantic + JSON schema)
2. **planner 엔드포인트 or 기존 generate 흐름에 플래너 단계 삽입**
3. **검증/폴백 로직** (허용 블록, 총 길이, quality/crisis 조건)
4. **decision_trace 기록** (planner_used, fallback_reason)

---

### 14.3 DSL(블록) 최소 스펙

**허용 블록 타입 (초기 6개)**

- `breath_regulation`, `body_release`, `defusion`, `self_compassion`, `activation`, `grounding`

**Pydantic 모델**

- **PlannerPlan**: `total_target_s: int`, `blocks: list[Block]`
- **Block**: `type: Literal["breath_regulation","body_release","defusion","self_compassion","activation","grounding"]`, `duration_s: int` (30~300), `intensity: float` (0~1)

**Block.intensity 용도 (명세 확정)**  
- 현재 NLG/타이밍에서 사용하지 않음. **향후 확장용** 필드(hold_ms·말 빠르기 보정 등). 구현 시 검증만 하고 downstream에는 전달만.

**블록 JSON 예시**

```json
{
  "total_target_s": 480,
  "blocks": [
    {"type": "breath_regulation", "duration_s": 120, "intensity": 0.4},
    {"type": "body_release",      "duration_s": 120, "intensity": 0.4},
    {"type": "defusion",          "duration_s": 180, "intensity": 0.3},
    {"type": "activation",        "duration_s": 60,  "intensity": 0.6}
  ]
}
```

**서버 검증 규칙**

- `blocks` 길이: **2~6**
- `duration_s` per block: **30~300**
- 합계: **sum(duration_s) within total_target_s ± 60**
- `intensity`: **0.0~1.0**
- 허용된 type만 (위 6개). 금지 블록 포함 시 폴백.

---

### 14.4 플래너 호출 시점 (명세 확정)

- **플래너는 `cursor == null` 인 요청(세션 시작 첫 Chunk)에서만 호출한다.**
- 두 번째 Chunk부터(`cursor` 있음)는 **이미 첫 Chunk에서 정한 scenario_blocks + next_cursor**만 사용. 플래너 재호출 없음.

---

### 14.5 crisis / emergency 정의 (명세 확정)

- **crisis_gate 또는 emergency** = 다음 중 하나라도 참이면 플래너 건너뛰고 **고정 플랜(grounding+breath)** 적용:
  - `signal_degrade == True` (기존 GuidanceGenerateRequest)
  - `confidence is not None and confidence < 0.4` (기존 failover)
  - (선택) 향후 crisis_gate 모듈에서 intake/별도 필드로 위기 판별 시 그 결과 True
- 구현 1단계: **signal_degrade 또는 confidence < 0.4** 만으로 crisis로 간주.

---

### 14.6 face_data.quality

- `face_data` 있고 **`face_data.quality < 0.5`** 이면 플래너 건너뛰고 기존 고정 시나리오(selected_theme_id 기반) 사용.
- 그 외(quality ≥ 0.5 또는 face_data 없음)에는 플래너 LLM 호출 후 JSON 수신 시도.

---

### 14.7 고정 플랜 형태 (명세 확정)

- **crisis/emergency 시 적용하는 고정 플랜** = **grounding + breath**만. 블록 2개, 고정 길이.
  - 블록 1: `type="grounding"`, `duration_s=120`
  - 블록 2: `type="breath_regulation"`, `duration_s=120`
- 총 4분 고정. `total_target_s`와 무관하게 항상 위 2블록만 실행.

---

### 14.8 서버 검증 + 폴백 (핵심)

**서버가 할 일 (LLM 신뢰하지 말기)**

- JSON 파싱 실패 → 폴백
- 스키마 불일치 → 폴백
- 금지 블록 포함 → 폴백
- 합계/범위 위반 → 폴백
- **crisis_gate=true** 면 무조건 고정 플랜(grounding + breath_regulation) 짧게
- **quality < 0.5** 면 플래너 무시, 기존 시나리오(또는 neutral)

**decision_trace에 기록**

- `planner_used`: true / false
- `planner_fallback_reason`: `"json_parse"` | `"schema"` | `"constraints"` | `"crisis"` | `"low_quality"` | …

---

### 14.9 LLM 프롬프트 (출력 강제 — 붙여넣기용)

목적: 문장 생성 금지, **JSON만** 출력.

```text
You are a planner. Output MUST be a single JSON object and nothing else.

Task:
Given the user's STRICT fields and recent session feedback, propose a safe sequence of meditation blocks.

Allowed block types:
["breath_regulation","body_release","defusion","self_compassion","activation","grounding"]

Constraints:
- Output JSON schema:
{
  "total_target_s": integer,
  "blocks": [{"type": string, "duration_s": integer, "intensity": number}]
}
- blocks length: 2 to 6
- duration_s per block: 30 to 300
- sum(duration_s) must be within total_target_s ± 60
- intensity: 0.0 to 1.0
- Do NOT output any text besides the JSON.
- Do NOT invent new block types.

Input STRICT:
{STRICT_PAYLOAD}

Recent feedback summary:
{FEEDBACK_SUMMARY}

Choose total_target_s based on user's state:
- high arousal / stress: 240~420s
- neutral: 360~600s
- low energy / sleepy: 240~480s with activation near the end

Return JSON only.
```

---

### 14.10 Cursor에 던질 명령 프롬프트 (복붙용)

```text
목표: 기존 명상 Guidance API에 '블록 플래너(LLM)' 단계를 최소로 추가해.
성공하면 LLM이 만든 blocks 순서로 시나리오를 실행하고, 실패하면 기존 scenarios.json 기반 고정 시나리오로 폴백해.
GPU 없어도 되니 외부 LLM 호출은 기존 NLG 호출 방식(vLLM or API) 중 하나로 붙여.

요구사항:
1) Pydantic 모델로 PlannerPlan(total_target_s:int, blocks:list[Block]) 추가.
   Block = {type: Literal["breath_regulation","body_release","defusion","self_compassion","activation","grounding"], duration_s:int(30~300), intensity:float(0~1)}

2) 기존 generate 흐름(세션 시작 첫 chunk, cursor==null)에
   - crisis_gate 또는 emergency 신호(signal_degrade==True 또는 confidence<0.4)면 planner 건너뛰고 고정 플랜(grounding+breath 2블록) 적용
   - face_data.quality < 0.5이면 planner 건너뛰고 기존 고정 시나리오 사용
   - 그 외엔 planner LLM 호출해서 JSON만 받기

3) 서버 검증: blocks 2~6개, sum(duration_s) within total_target_s ± 60, 위반 시 폴백

4) decision_trace에 planner_used, planner_fallback_reason 기록

5) 기존 기능 회귀 금지: planner 실패 시 현재 동작 그대로 유지.

출력: 변경된 파일 목록, 핵심 코드 diff, 유닛 테스트 3개(정상/파싱 실패/constraint 위반 폴백).
```

---

### 14.11 구현 시 참고 (코드 위치)

- **LLM 호출**: `backend/services/nlg_service.py` 등 기존 NLG 호출 경로(vLLM or API) 재사용.
- **시나리오 선택**: `backend/core/policy_engine.py`의 `decide_action(...)` — 여기 직전 또는 generate 첫 Chunk(cursor==null)에서 플래너 호출 후, 성공 시 scenario_blocks만 PlannerPlan.blocks에서 변환해 채우고 `scenario_id="planner_custom"` 등으로 전달.
- **플래너 blocks → ScenarioBlock**: 블록 type별 base_text/adapt_instruction 매핑표는 scenarios.json 또는 별도 템플릿으로 정의 후, PlannerPlan.blocks를 ScenarioBlock 리스트로 변환해 기존 Chunk 흐름에 넣으면 됨. (매핑표 상세는 별도 문서 또는 §14 확장.)

---

### 14.12 구현 시 명확화 사항 (보완)

구현 시 착각·불일치를 줄이기 위해 아래를 명세로 확정한다.

| 항목 | 명세 |
|------|------|
| **total_target_s 출처** | **total_target_s는 LLM 출력만 사용**한다. (서버는 LLM이 준 값을 검증만 함.) 선택: 프롬프트에 `intake.available_time`(분)→초 환산값 또는 기본값(예: 480)을 힌트로 넣어 줄 수 있음. |
| **FEEDBACK_SUMMARY 기본값** | 피드백이 없을 때(첫 세션 등): `{FEEDBACK_SUMMARY}` 를 **빈 문자열 `""` 또는 `"No prior feedback"`** 로 치환한다. |
| **crisis 고정 플랜 2블록 정의** | crisis 시 적용하는 **grounding 120s + breath_regulation 120s** 2블록은, **scenarios.json에 `crisis_grounding` 같은 키로 두거나, 코드 내 고정 ScenarioBlock 리스트**로 정의한다. (기존 standard_grounding을 재사용해도 됨.) |
| **fallback_reason 필드명** | decision_trace에 기록할 때 **필드명은 `planner_fallback_reason` 하나로 통일**한다. trace가 문자열 배열이면 `"planner_fallback_reason: json_parse"` 형태의 한 줄로 넣는다. |
| **intensity 범위 위반** | Block.intensity는 **0.0~1.0**. LLM이 범위 밖(예: 1.2, -0.1)을 주면 **Pydantic 검증 실패 → 스키마 불일치 → 폴백**으로 처리한다. |

---

이 문서는 현재 구현된 명상 가이드 서비스를 설계 명세 형태로 정리한 것입니다. §12·§13은 갭 분석 및 연산 속도 전략, §14는 **블록 플래너(LLM) 추가 시** 구현·검토·복붙용 **통합 명세**입니다.
