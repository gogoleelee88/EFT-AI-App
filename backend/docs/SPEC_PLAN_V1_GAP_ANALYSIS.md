# 계획서 v1 vs SPEC.md 대조 결과: 누락·모호·충돌

**대상**: `SPEC_OMISSION_PREVENTION_PLAN_V1.md` vs `SPEC.md`  
**목적**: 누락/모호/충돌 식별. 코드 작성 전 결정용.

## 1. 누락된 요구사항 목록 (원문 인용 포함)

아래는 SPEC에 명시되어 있으나 계획서 v1에 **항목·파일트리·API·체크리스트·위험** 중 한 곳에도 반영되지 않았거나, 문구가 약한 항목이다.

| # | SPEC 원문 인용 | 위치 | 계획서 v1 상태 |
|---|----------------|------|----------------|
| 1 | **「Level 0(기본): 30초 체크인(질문 1~3개, 선택지 5개 이하)로만 수집」** | F1 | 체크인 “질문 1~3개, 선택지 5개 이하”는 있으나 **“30초 체크인”** 시간 제약이 체크리스트·API 요약·검증 레이어에 없음. |
| 2 | **「보조 추론은 항상 inferred=true로 명시 표기(사용자에게도 “추정” 라벨)」** | F1 | Condition 검증·체크리스트에 “추정” 라벨/ inferred 표기 요구가 명시되지 않음. |
| 3 | **「구현 형태: 단일 FastAPI(또는 Node) 모놀리스 내부에 6개 모듈 + Redis(또는 DB 기반) Job Queue」** | C1 | 파일 트리에서 **Job Queue가 Redis vs DB 기반**인지 결정·표기가 없음. |
| 4 | **「트리거: 새로운 Condition 저장(POST /condition/checkin) 후, 서버가 condition_score 계산 → 필요 시 POST /adapt/day 내부 호출(또는 클라이언트가 호출)」** | F5 | checkin 후 **서버 내부에서 /adapt/day 호출할지, 클라이언트만 호출할지** 계획서에 선택지/결정이 없음. |
| 5 | **「delay: … Scheduler가 DayPlan 간 이동 + 알림 재설정」** | F5 | Adapter의 delay는 계획서에 있으나 **“알림 재설정”** 역할이 Scheduler 책임으로만 명시되어 있지 않음. |
| 6 | **「원칙: “기분”보다 START/RESUME 같은 행동 이벤트가 1순위 KPI」** | E | KPI/이벤트 설계 8개와 **“행동 이벤트 1순위”** 원칙이 체크리스트·모듈 책임에 반영되지 않음. |
| 7 | **「EFT(또는 규정된 60초 기법) 후 5분 내 START율」**, **「이벤트: RESISTANCE_TECHNIQUE_END → 5분 윈도우 내 TASK_START」** | E | RESISTANCE_TECHNIQUE_END, 5분 윈도우 내 TASK_START 등 **KPI 이벤트·로그 필드**가 ExecutionLog/이벤트 설계에 명시되지 않음. |
| 8 | **「저항 이벤트당 ‘2분 행동 잠금’ 준수율」**, **「이벤트: LOCK_APPLIED 후 LOCK_EXPIRED까지 이탈 없는지」** | E | LOCK_APPLIED, LOCK_EXPIRED **이벤트 타입/필드**가 ExecutionLog 스키마·체크리스트에 없음. |
| 9 | **「DayPlan 생성→첫 START까지 시간(TTFS: Time To First Start)」** | E | TTFS 계산을 위한 **DayPlan 생성 시점·첫 TASK_START 시점** 로깅/쿼리 요구가 계획서에 없음. |
| 10 | **「모드(40/70/100)별 완료율/중단율」**, **「Adapt 호출 후 30분 내 RESUME율」**, **「질문 수(체크인+저항) / 일」**, **「Drop/Shrink/Swap 후 … 괴리 감소율」**, **「3일 연속 START streak」** | E | KPI 8개에 대한 **집계 가능한 로그/필드·쿼리 요구**가 DB·API·체크리스트에 명시되지 않음. |
| 11 | **「70/40을 “성공 확률 레일”로 명명 + 하향 시 “보호/최적화” 문구 고정」** | D | 계획서에는 “시작 성공률을 우선” 1줄만 있음. **“보호/최적화”** 문구가 별도로 명시되지 않음. |
| 12 | **「Condition: condition_id, date_time, min_condition_set, source_level(0/1/2), inferred_flags」** | C3 | DB/스키마에는 `ts` 사용. SPEC C3는 **date_time** 필드명 사용 → 명시적 매핑(date_time ↔ ts) 없음. |
| 13 | **「ExecutionLog: log_id, task_id, day_id, event_type(START/STOP/COMPLETE/RESUME), ts, context」** | C3 | C3에는 **context**만 있고, E 스키마에는 duration_sec, mode, condition_ref, resistance_event_ref, metrics 등이 있음. 계획서는 E 기준. **C3의 context**가 E의 metrics/context와 동일한지 정의 없음. |
| 14 | **「위기 징후는 별도 안내(제품 안전 문구)」** | D | “진단/치료 금지”만 체크리스트에 있음. **위기 징후 시 별도 안내·제품 안전 문구** 요구가 누락됨. |

## 2. 모호한 부분 (결정 필요) — 질문 최대 5개

아래 5개는 구현 전에 **한 번씩 결정**이 필요하다.

| # | 모호한 부분 | SPEC 근거 | 결정이 필요한 질문 |
|---|-------------|-----------|---------------------|
| 1 | **checkin 후 Adapt 호출 주체** | F5: “서버가 … 필요 시 POST /adapt/day **내부 호출(또는 클라이언트가 호출)**” | 서버가 condition_score 계산 후 **자동으로** adapt를 내부 호출할지, 항상 클라이언트가 별도 POST /adapt/day를 호출할지 정할 것. (임상·일관성에 영향) |
| 2 | **모드 “하루 1회”의 범위** | B1: “전환은 **하루 1회 기본** + 이벤트 기반 예외” | “하루 1회”가 **당일 첫 체크인 기준 1회**인지, **모드 값 변경 횟수** 1회인지, **사용자가 수동 변경하는 횟수** 1회인지 정의할 것. |
| 3 | **“이벤트 기반 예외”의 구체 조건** | B1: “이벤트 기반 예외(**저항 폭주/통증 급증 등**)” | 저항 폭주(예: N회/시간), 통증 급증(예: pain 상승량 또는 절대값) 등 **예외로 인정할 구체 조건**을 열거할 것. |
| 4 | **30초 체크인** | F1: “**30초 체크인**(질문 1~3개…)” | 30초가 **체크인 완료 허용 시간(UX 타이머)**인지, **체크인 소요 시간 목표**인지, **백엔드 검증 대상**인지 결정할 것. |
| 5 | **Job Queue 구현체** | C1: “**Redis(또는 DB 기반)** Job Queue” | Redis vs DB 기반 중 어떤 것을 1차로 사용할지(운영·배포 복잡도 기준) 정할 것. |

## 3. 충돌하는 규칙 + 우선순위 제안 (임상 안전/보호 규칙 우선)

SPEC 내에서 서로 겹치거나, 적용 순서에 따라 결과가 달라질 수 있는 부분만 정리했다. **임상 안전·신체 보호 규칙을 최우선**으로 두는 우선순위를 제안한다.

| # | 충돌·겹침 설명 | 관련 규칙 | 우선순위 제안 |
|---|----------------|-----------|----------------|
| 1 | **모드 결정: score 구간 vs pain 강제** | F4: “score>=70→100, … score<40→40” vs “pain>=7이면 **score와 무관하게** 최대 70, pain>=9이면 40 강제” | **1순위: pain 안전 규칙.** 모드 결정 시 먼저 pain>=9 → 40, pain>=7 → max 70 적용한 뒤, 필요 시에만 score 구간 적용. (D “통증/생리 … 무시 금지”와 일치) |
| 2 | **모드 상향 vs 당일 1회 제한** | B1: “모드 상향은 최근 3회 연속 START 성공 … **있을 때만**” vs “전환은 **하루 1회 기본**” | **1순위: 하루 1회 제한.** 같은 날 이미 1회 전환했으면, “3회 연속 START”가 있어도 **그날** 추가 상향은 허용하지 않거나, “이벤트 기반 예외”로만 허용. 2순위: 3회 연속 START는 “다음 날” 상향 허용 조건으로 사용. |
| 3 | **감정기법 30~90초 vs “60초 기법”** | B3: “(30~90초) 감정기법” / E: “**EFT(또는 규정된 60초 기법)** 후 5분 내 START율” | **충돌 아님.** 60초는 “규정된 한 가지 기법” 예시. 30~90초 범위(및 90초 상한)를 그대로 적용하고, KPI 집계 시 “규정된 60초 기법”은 30~90초 내 선택된 duration_sec로 정의하면 됨. **우선순위:** B3 30~90초·90초 상한 유지. |
| 4 | **체크인 required: condition_id·ts** | F3 Condition 스키마: required에 **condition_id**, **ts** 포함. 실제로 checkin **요청** 시 condition_id는 서버가 생성. | **해결:** 요청 스키마와 저장/응답 스키마를 구분. 요청에는 condition_id 불필요. 응답·DB·내부 Condition 객체에는 condition_id, ts 필수. 검증 레이어는 “저장/응답용”에만 F3 전체 스키마 적용. |
| 5 | **D “보호/최적화” vs B1 “시작 성공률을 우선”** | D: “하향 시 **보호/최적화** 문구 고정” / B1: “**수면/피로/통증 신호로 인해 시작 성공률을 우선합니다.**” | **충돌 아님.** B1이 구체 1줄 문구. D “보호/최적화”는 70/40 레일 명명 맥락. **우선순위:** B1 1줄 문구를 기본으로 하고, UI에서 70/40 설명 시 “보호·최적화” 단어를 함께 쓸 수 있음. 계획서에 “보호/최적화” 문구를 체크리스트에 추가 권장. |
| 6 | **Adapt “필요 시” 호출** | F5: “**필요 시** POST /adapt/day 내부 호출(또는 클라이언트가 호출)” | “필요 시” = 모드 하향·score 구간 변경·pain 강제 등으로 **당일 계획과 모드가 어긋날 때**만. **우선순위:** (1) pain/모드 안전 규칙 적용 후, (2) 현재 DayPlan.mode가 새 모드와 다르거나 score가 구간 경계를 넘으면 adapt 호출. |

**요약:**  
- **항상 우선:** pain>=9 → 40, pain>=7 → 최대 70 (그 다음 score 구간).  
- **그 다음:** 당일 모드 전환 1회 제한, 그 다음 “3회 연속 START” 등 상향 조건.  
- **Adapt:** “필요 시”는 모드/score 변경이 있을 때로 정의하고, 내부 호출 vs 클라이언트 호출은 2절 질문 1에서 결정.
